## Overview

During Week 6–7, my main contribution was related to testing, validation, documentation, and demonstration preparation for the new EduOS programming evaluator.

Since the evaluator executes student-written C++ programs, different failure cases had to be checked to ensure that incorrect student code did not crash or freeze the complete EduOS student application.

## Functional Testing

The evaluator was tested using different types of C++ programs.

The main test situations included:

- program producing the correct output,
- program producing incorrect output,
- one test case passing and another failing,
- C++ syntax/compilation error,
- program producing no output,
- multiline input and output,
- runtime failure,
- infinite loop.

The interface was checked to make sure each case produced an understandable result for the student.

## Timeout Testing

An infinite-loop program was used to verify that a student's program could not run indefinitely.

The evaluator terminates execution after the configured timeout and reports a **Time Limit Exceeded** condition instead of allowing the student interface to remain permanently stuck.

This was an important test because programming students can accidentally create infinite loops during normal lab work.

## Compilation Error Testing

Programs containing invalid C++ syntax were also tested.

Instead of attempting to execute the program, EduOS displays the compiler error information to the student.

This makes the evaluator useful not only for final checking but also during development of the student's solution.

## Output Verification Testing

Different output formats were checked to verify the comparison behavior.

Minor formatting differences such as trailing whitespace and final newlines are normalized before comparison.

Actual value differences still correctly produce a failed result.

## Regression Testing

Existing EduOS features were also checked after evaluator integration.

The main areas considered were:

- existing student accounts,
- separate student home directories,
- student application startup,
- administrator login,
- existing task display,
- student task assignment,
- ArchISO boot process,
- XFCE/SDDM session behavior.

The purpose was to ensure that evaluator changes did not damage the previously working multi-user environment.

## Build and VM Testing

Updated versions of EduOS were built through the ArchISO profile and tested inside QEMU/KVM before demonstration.

Separate build-output directories were used for newer development versions.

Old generated ISO files were cleaned when necessary so that outdated images were not accidentally launched during testing.

A previously known working EduOS ISO was kept separately as a backup.

## Demo Preparation

A simple demonstration sequence was prepared for the evaluator.

The planned flow is:

1. Log in using the administrator account.
2. Create or edit a C++ lab question.
3. Add two test cases and their expected outputs.
4. Log out of the administrator account.
5. Log in as a student.
6. Open the assigned task.
7. Write a correct C++ solution.
8. Run the evaluator and demonstrate passing tests.
9. Modify the solution to produce an incorrect answer.
10. Run the evaluator again and demonstrate a failed test.
11. Introduce a compilation error to demonstrate compiler-error handling.
12. Optionally use an infinite loop to demonstrate timeout protection.

This sequence demonstrates both the normal operation and important failure cases of the system.

## Documentation

The evaluator workflow was documented as a distinct EduOS component rather than being described as EduLab.

The current implementation uses local C++ compilation and execution.

Stronger isolation using containers or a separate EduLab environment is kept as future work and should not be claimed as part of the current prototype.

## Current State

By the end of Week 7, the evaluator had been integrated and tested successfully for C++ lab exercises.

Students can now receive a programming question, write code, run it against predefined test cases, and immediately view the evaluation result.

## Next Step

This will require verifying:

## Conclusion

Week 6–7 concentrated on making the new evaluator reliable enough for demonstration. Testing multiple execution conditions helped verify that EduOS can handle both correct and incorrect student programs without disrupting the rest of the student environment. The system is now ready for the next stage involving persistent code submission.
