## Overview

During this phase, my contribution was mainly focused on the student submission workflow, administrator monitoring of submissions, and validation of the updated EduOS lab system.

The objective was to complete the workflow from assignment creation to student submission without implementing automatic code evaluation yet.

This allowed the team to verify that the core academic interaction works before introducing the EduLab evaluator.

## Simplified Student Submission Workflow

The initial assignment prototype allowed students to either paste code or create a separate submission file.

This was simplified because allowing students to manually choose filenames and filesystem locations was unnecessary and would complicate future evaluation.

The student now has only one submission method:

**Type or paste source code directly into the EduOS code editor.**

When a problem is opened, the student sees:

- Problem title
- Full problem statement
- Programming language
- Code editor
- Submit Code button

No upload or file-selection interface is shown.

## Internal Submission Storage

Although students only interact with the graphical code editor, EduOS still stores the submitted source internally as a normal program file.

The filename is automatically selected by EduOS according to the language.

Examples include:

- C++ → `source.cpp`
- C → `source.c`
- Java → `Main.java`
- Python → `solution.py`

Students therefore do not control filesystem paths or filenames.

Each submission is associated with:

- Authenticated Linux username
- Lab assignment ID
- Problem ID

Submission metadata also stores information such as:

- Submission time
- Programming language
- Submission status

This structure will later allow the EduLab evaluator to directly locate the source code for compilation and testing.

## Submission Progress Tracking

The system calculates lab progress using the number of submitted problems.

For a lab containing three questions:

- 0 / 3 submitted → Not Started
- 1 / 3 or 2 / 3 → In Progress
- 3 / 3 → Submitted

The student dashboard displays this progress so that students can easily see which lab work remains incomplete.

Resubmitting a problem updates the existing submission rather than requiring the student to create another file.

## Administrator Submission Monitoring

The administrator dashboard was extended so that the teacher can inspect the progress of individual students.

When a student is selected, the administrator can see:

- Labs assigned to that student
- Current lab status
- Number of completed problems
- Number of total problems

The administrator can then open a lab and inspect submission status for each question.

For example:

- Q1 – Submitted
- Q2 – Pending
- Q3 – Submitted

For submitted questions, the teacher can open the student's source code in a read-only viewer.

The administrator cannot modify the submitted source through this view.

## Secure Submission Access

The administrator GUI continues to run as a normal Linux user rather than running with full root privileges.

Access to student submission information is handled through the existing restricted helper design.

Requests are validated using:

- Student username
- Assignment ID
- Problem ID

Arbitrary filesystem paths are not accepted.

This avoids introducing a generic file-reading or shell interface simply to allow the teacher to inspect submissions.

Student submission storage is also separated by Linux username so that one student cannot select or access another student's submission directory.

## Testing and Validation

Testing during this phase focused on both the new academic workflow and regression of existing functionality.

Important cases included:

- Assignment creation
- Multiple problems in one lab
- Assignment editing
- Student-specific assignment visibility
- Typed code submission
- Resubmission
- Submission metadata
- Correct completion status
- Administrator submission viewing
- Rejection of invalid usernames
- Rejection of invalid assignment/problem IDs
- Prevention of cross-student submission access
- Preservation of existing student login behaviour
- Preservation of existing administrator functions

The evaluator itself was deliberately excluded from testing because it has not yet been implemented.

## Current State

At the end of this phase:

- Students can open individual programming problems
- Students submit only through the built-in code editor
- EduOS automatically stores source files
- Submission progress is tracked per problem
- Administrators can view student lab progress
- Administrators can inspect submitted code
- Student submission directories remain isolated
- No code execution or grading is performed yet

## Next Step

The next major development phase will introduce the EduLab evaluator.

The existing submission structure can be used as the evaluator input, allowing future components to:

- Compile submitted code
- Execute test cases
- Apply resource limits
- Compare program output
- Generate marks and feedback

## Conclusion

This phase completed the basic teacher-to-student lab workflow. EduOS can now distribute structured lab problems, accept source-code submissions and allow teachers to inspect student progress and answers. The system is therefore ready for the next stage of development, where automatic code evaluation can be added on top of the existing submission architecture.
