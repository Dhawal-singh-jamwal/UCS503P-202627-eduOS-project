## Overview

During this development phase, my primary contribution was focused on improving the academic workflow and redesigning the lab assignment structure used by EduOS.

The previous prototype contained both a general "Tasks" section and a separate "Lab Assignments" section. This created unnecessary duplication because both represented academic work assigned by a teacher.

The objective of this phase was to develop a single structured lab assignment system that can later connect naturally with the EduLab evaluator.

## Unifying Tasks and Lab Assignments

The previous interface displayed both:

- Tasks
- Lab Assignments

The academic workflow was simplified so that teacher-created coursework is now represented only through **Lab Assignments**.

The older task data can remain internally for backward compatibility, but it is no longer treated as a separate feature in the user interface.

This results in a clearer hierarchy:

Lab Assignment  
→ Problems  
→ Student Answers

This structure is closer to the way practical programming labs are conducted.

## Lab Assignment Data Model

The Lab Assignment structure was expanded.

Earlier, one assignment directly contained one problem statement.

The new model allows one lab assignment to contain multiple programming problems.

For example:

**Data Structures Lab 4**

- Q1 – Array Rotation
- Q2 – Frequency Map
- Q3 – Prefix Sum

Each assignment contains information such as:

- Assignment ID
- Assignment title
- Description
- Due information
- Assigned students
- Creation information
- List of problems

Each problem contains:

- Problem ID
- Problem title
- Problem statement
- Programming language

Assignment IDs remain stable while individual problem IDs remain unique within the assignment.

## Administrator Assignment Workflow

The administrator dashboard was expanded with a dedicated Lab Assignments interface.

The teacher can now create a complete lab assignment by entering:

- Assignment title
- Description
- Due information
- Students who should receive the lab

Students can be individually selected or selected together using options such as Select All and Clear All.

After creating the lab, the teacher can add multiple problems inside the assignment.

Each problem provides a multiline problem statement field so that complete programming questions can be entered rather than only short task descriptions.

The administrator can also:

- Edit assignments
- Delete assignments
- Add problems
- Edit problems
- Delete problems
- Change which students receive the assignment

## Student Lab Dashboard

The student interface was redesigned around the new assignment hierarchy.

Instead of showing Tasks and Lab Assignments separately, the student now sees one Lab Assignments section.

Each lab displays important information such as:

- Lab title
- Lab ID
- Due date
- Number of problems
- Number of submitted problems
- Current completion status

Possible assignment states include:

- Not Started
- In Progress
- Submitted

Opening a lab displays all of its problems separately.

For example:

- Q1 – Array Rotation
- Q2 – Frequency Map
- Q3 – Prefix Sum

Each problem also displays whether it has already been submitted.

## Student-Specific Assignment Visibility

The assignment architecture was also improved so that students only receive coursework actually assigned to them.

Instead of depending only on graphical filtering, student-specific assignment data is generated for each Linux student account.

This allows Linux file permissions to assist in enforcing visibility.

For example, if a lab is assigned only to `student1000` and `student1002`:

- `student1000` can view it
- `student1002` can view it
- `student1001` does not receive it

If the administrator later removes a student from the assignment, the student's assignment view is updated accordingly.

## Current State

At the end of this phase:

- Tasks and Lab Assignments have been unified
- Lab Assignments are the main academic coursework model
- One lab can contain multiple programming questions
- Teachers can select specific students
- Problem statements support detailed multiline questions
- Students see only their assigned labs
- Students can open individual problems
- Progress is shown using submitted problem counts

## Next Step

The next extension of the assignment model will be integration with the EduLab evaluator.

Each problem can later include:

- Test cases
- Expected output
- Resource limits
- Evaluation rules

These features were intentionally not implemented during this phase so that assignment creation and distribution could first be tested independently.

## Conclusion

This phase established a more realistic academic workflow for EduOS. Lab work is now organized as assignments containing multiple problems rather than unrelated task entries. This provides a cleaner interface for both teachers and students and creates a suitable structure for future automated evaluation.
