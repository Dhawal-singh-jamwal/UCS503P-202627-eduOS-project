## Overview

During Week 6–7, my work mainly focused on extending the academic-task design of EduOS so that programming lab questions could be represented properly and used by the new evaluator.

The previous task model mainly contained general task information. For programming evaluation, additional information was required such as the problem statement, programming language, test-case input, and expected output.

## Programming Task Design

The task structure was extended to support C++ lab exercises.

A programming task can now contain information such as:

- task title,
- status,
- due date,
- programming language,
- problem statement,
- Test Case 1 input,
- Test Case 1 expected output,
- Test Case 2 input,
- Test Case 2 expected output.

The design was kept compatible with the existing EduOS task format so that older tasks without evaluator-related fields would still remain valid.

## Administrator Workflow

The administrator-side task workflow was reviewed and extended so that lab questions can be configured directly through EduOS.

The intended workflow is:

**Administrator → Create/Edit Task → Enter Question → Configure Test Cases → Save Task**

The student application then reads the same task information and presents it to the correct student.

This creates a clear data flow between task creation and student evaluation without introducing a separate database at the current prototype stage.

## Evaluator Architecture

The evaluator was designed as a separate software component.

The logical interaction is:

**Admin Dashboard → Task Data → Student Application → Evaluator → C++ Compiler → Test Results**

Keeping the evaluator separate from the user interface makes the design more modular.

It also gives the project a clearer component structure for future development, where the local evaluator may later be replaced or extended using stronger isolation mechanisms.

## Output Comparison Design

A simple comparison policy was selected for the prototype.

The evaluator ignores insignificant trailing whitespace and final newline differences while still detecting meaningful output differences.

For example, outputs such as:

`5`

and

`5` followed by a newline

can be considered equivalent.

However, genuinely different output values continue to produce a failed test case.

## Backward Compatibility

An important design requirement was that existing task data should continue working after evaluator support was introduced.

Tasks without:

- a programming language,
- a question,
- or test cases

must still load normally.

This prevents the evaluator addition from breaking previously created EduOS data.

## UML and System Design

The new evaluator functionality was also considered in the system architecture.

The important components now include:

- EduOS Student Application,
- EduOS Admin Dashboard,
- Student/Task Data,
- EduOS Evaluator,
- C++ Compiler,
- student Linux environment.

The evaluator is treated as an EduOS component and is separate from the future **EduLab** execution infrastructure.

EduLab remains future work involving stronger isolated or containerized execution.

## Submission Workflow Planning

After the evaluator became functional, the next system requirement identified was permanent code submission.

The planned distinction is:

- **Run Tests** — evaluate the current code without saving a submission.
- **Submit Code** — evaluate the current code again and store the submitted source and result.

A future submission record will be associated with both a specific student and a stable task identifier.

## Current State

By the end of Week 7, the project design supports the complete flow from teacher-created programming task to student-side evaluation.

The architecture remains intentionally local for the current proof-of-concept and does not yet depend on FastAPI, PostgreSQL, containers, or a central server.

## Next Step

The next step is to complete the submission model and administrator submission-viewing workflow.

This will allow the teacher to inspect a student's submitted C++ source code and its corresponding test result.

## Conclusion

The work during Week 6–7 helped convert EduOS from a system that only displayed academic tasks into one capable of representing and evaluating programming lab exercises. The updated task structure and evaluator architecture also provide a clearer base for future submission management and automated grading.
