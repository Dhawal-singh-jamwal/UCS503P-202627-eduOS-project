## Objectives for the Reporting Period

The main objective during this period was to improve the architecture of EduOS to support the newly introduced machine-management and EduLab components.

The focus was on defining how information moves between different modules, organizing the data structures required by the platform and maintaining a clear separation between student and administrator privileges.

## Week 1 — Machine Management Architecture and Data Design

### Work Completed

**1. Laboratory Profile Architecture**

Worked on defining a profile-based approach for managing laboratory computers.

Each machine is associated with a laboratory profile containing the software requirements necessary for its intended academic use.

For example, a C++ laboratory profile may specify compilers, debugging utilities and other development tools.

The profile-based design allows the administrator to describe the expected configuration without manually configuring each machine independently.

**2. Machine Registration and Status Model**

Studied and documented the machine registration process.

The registration model includes information such as:

- Unique machine identifier.
- System hostname.
- Assigned laboratory profile.
- Registration status.
- Latest configuration compliance status.

The purpose was to support a consistent relationship between a registered machine and its intended software environment.

**3. Configuration Drift and Synchronization Workflow**

Designed the logical workflow used by the EduOS Agent to compare the current machine configuration against the requirements defined by its assigned profile.

The workflow involves reading the laboratory profile, checking required software packages and services, identifying configuration differences and reporting the result to the administrator.

Synchronization was designed as a controlled administrative operation that attempts to restore missing requirements.

**4. Student Lifecycle and Persistence Design**

Reviewed the data structures required for creating, modifying and deleting student records.

Particular attention was given to the relationship between Linux accounts, academic metadata and persistent state.

Considered the issue of deleted students being recreated during startup and the need for a reliable source of truth when restoring account information.

## Week 2 — EduLab Architecture and Assessment Design

### Work Completed

**1. Assessment Data Model**

Worked on designing the structure of an EduLab assessment.

An assessment contains important attributes such as:

- Assessment identifier and title.
- Scheduled start time.
- Assessment duration.
- Assessment instructions.
- One or more programming questions.
- Maximum marks for each question.
- Public examples and hidden test cases.

Stable identifiers were considered important to ensure that questions and results remain correctly associated even when assessment content changes.

**2. Assessment Lifecycle Design**

Defined the intended sequence of operations from assessment creation to final result generation.

The main workflow consists of:

1. Administrator creates the assessment.
2. Questions and test cases are configured.
3. Assessment is saved and activated.
4. Eligible students access the assessment.
5. An attempt is created with a deadline.
6. Student code is saved during the assessment.
7. Code is evaluated when submitted or when time expires.
8. Scores and attempt status are stored for later review.

**3. Hidden Test Security**

Reviewed the security requirements for protecting hidden test cases.

The main design principle was that students should receive only the public assessment information needed to solve questions.

Hidden inputs and expected outputs should remain in protected storage and be accessed only by the authorized evaluation component.

Also reviewed the importance of executing submitted C++ programs under an unprivileged account rather than giving arbitrary student code root permissions.

**4. Automated Scoring Design**

Worked on defining a deterministic scoring method based on hidden test-case results.

For each question, the awarded marks are calculated according to the number of tests passed relative to the total number of tests.

For example, if a question carries 10 marks and the solution passes three out of four test cases, the score is 7.5 marks.

Individual question scores are combined to produce the overall assessment score.

**5. Assessment Lockdown and Monitoring Design**

Reviewed the requirements for fullscreen assessment behavior and basic anti-cheating restrictions.

This included consideration of window-switching attempts, fullscreen exit detection, clipboard restrictions and event logging.

The design treats these controls as best-effort monitoring rather than guaranteeing that cheating is impossible.

**6. System Architecture and UML Documentation**

Updated the architectural understanding of EduOS to reflect the addition of administrative operations, evaluator integration, persistent storage, machine profiles and EduLab.

Reviewed component relationships and deployment structure, distinguishing the implemented local services from future centralized components.
