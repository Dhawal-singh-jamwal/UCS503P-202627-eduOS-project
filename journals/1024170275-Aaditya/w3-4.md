# EduOS Design Journal - Week 3-4

**Project:** EduOS - Academic Computing Platform  
**Member:** Aaditya Kumar Yadav  
**Period:** Week 3-4

## Overview

During Weeks 3 and 4, I mainly worked on refining the design of EduOS and defining how the different system components should interact.

The focus was on organizing the architecture, defining the student academic workflow, preparing student and task data, and creating system diagrams that represent both the current prototype and future planned modules.

## System Architecture

The EduOS architecture was organized into major functional areas:

- EduOS Client
- Management Layer
- EduLab Layer
- Infrastructure Layer

The EduOS Client represents the operating environment used by students.

The Management Layer is responsible for functions such as user management, machine registration, and laboratory profile assignment.

The EduLab Layer handles tasks, submissions, automated evaluation, and results.

The Infrastructure Layer supports deployment, storage, virtual machines, and containerized services.

## Student Workflow

The full student workflow was refined so that the prototype follows a clear academic process.

The workflow is:

**Login → Identify Student → Retrieve Assigned Tasks → Perform Task → Submit Work → Evaluate Submission → Store Result → Display Feedback**

This flow was used as the basis for the UML and Data Flow Diagrams.

## Student and Task Data

The current prototype uses a local JSON file to associate Linux users with student information.

The data includes:

- Linux username
- Roll number
- Student name
- Assigned academic tasks
- Task status
- Due information

Different students were given different task sets so that the system can demonstrate personalized academic content.

The current local data model was also designed so that it can later be replaced by a centralized API and database.

## Authentication and Academic Data

An important design decision was to separate operating-system authentication from academic information.

Linux handles the actual user authentication.

The EduOS application then reads the already authenticated Linux username and uses it to retrieve the correct academic record.

This avoids creating a second login system inside the application and keeps the workflow simpler.

## Data Flow Design

The Level 1 Data Flow Diagram divides EduOS into major processes such as:

- Authentication and User Management
- Machine Registration and Profile Management
- EduOS Agent and System Configuration
- Task and Submission Management
- Evaluation Management
- Results Management

The Level 2 diagram further breaks down task and submission handling into smaller processes such as task retrieval, submission validation, storage, and sending work for evaluation.

## Future Backend Planning

The current prototype uses local structured data, but the future system will use a centralized backend.

The planned flow is:

**EduOS Client → Management API → Database**

The backend will later manage:

- Students
- Machines
- Laboratory profiles
- Tasks
- Submissions
- Evaluation results
- Feedback

## Current State

The system design now clearly connects the current working prototype with the larger EduOS architecture.

The existing prototype already demonstrates the client-side flow of authentication, student identification, and personalized task display.

## Next Step

The next step is to begin converting the planned architecture into actual backend modules and API endpoints.

This will include user management, machine registration, task distribution, submission handling, and evaluation.
