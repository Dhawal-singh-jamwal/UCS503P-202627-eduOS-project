## Overview

During Week 6–7, my main focus was on extending EduOS from a personalized student environment into a system capable of executing and evaluating programming lab work. The major addition during this period was the first working version of the **EduOS Evaluator**, initially supporting C++ programs.

The aim was to allow a student to open an assigned programming task, write C++ code, execute it against predefined test cases, and immediately view whether the generated output matched the expected output.

## C++ Evaluator Implementation

A separate evaluator component was integrated with the existing EduOS student application.

The evaluation flow is:

- Student opens an assigned C++ lab task.
- The problem statement and test cases are loaded from EduOS task data.
- The student writes C++ code in the student interface.
- The student selects **Run Tests**.
- EduOS compiles the code using `g++`.
- The generated executable is run separately for each configured test case.
- Program output is compared with the expected output.
- PASS or FAIL is displayed for each test case.

The evaluator was kept as a separate component rather than placing compilation logic directly inside the graphical interface. This keeps the system modular and allows the evaluator to be extended later.

## Compilation and Execution Handling

The evaluator creates a temporary working directory for every evaluation.

The basic execution process is:

1. Store the student's source code temporarily as a C++ source file.
2. Compile it using `g++`.
3. Check whether compilation succeeded.
4. Execute the program separately for each test case.
5. Send the configured test input through standard input.
6. Capture standard output and error output.
7. Compare the result with the expected output.
8. Remove temporary files after evaluation.

Compilation errors are returned to the student application instead of crashing the program.

## Runtime Protection

Basic safeguards were also added to prevent normal programming mistakes from freezing the student environment.

These include:

- execution timeout for individual test cases,
- handling infinite loops,
- output-size limits,
- runtime-error detection,
- temporary execution directories,
- no use of `sudo`,
- no use of `shell=True`.

The current evaluator is intended as a proof-of-concept and not as a production-grade sandbox for malicious native programs.

## Student Interface Integration

The student application was extended with a simple C++ coding workspace.

The interface now contains:

- task title,
- programming question,
- editable C++ source-code area,
- **Run Tests** button,
- individual test-case results,
- expected output,
- actual output,
- overall number of test cases passed.

A simple editor was intentionally used rather than building a complete IDE.

## Testing and Debugging

Several cases were tested during implementation:

- correct C++ program,
- incorrect program output,
- compilation errors,
- multiline input,
- whitespace differences,
- runtime failures,
- infinite loops and timeout handling.

The evaluator was also checked to ensure that old EduOS tasks without programming-test data continue to work without crashing the student application.

## ISO Integration

The evaluator and required C++ compiler were integrated into the ArchISO profile so that the functionality is available directly inside the generated EduOS image.

The updated ISO was rebuilt and tested using QEMU/KVM.

Old development ISOs were also cleaned from the separate build-output directory to avoid confusion between previous and current builds.

## Current State

At the end of Week 7:

- EduOS successfully boots as a custom Arch-based ISO.
- Student Linux accounts continue to work independently.
- The student application opens automatically.
- Admin-created C++ lab questions can contain test cases.
- Students can write C++ code inside EduOS.
- Code can be compiled and executed locally.
- Results are checked against teacher-defined expected outputs.
- Compilation errors and execution timeouts are handled safely.
- Existing student and administrator functionality remains operational.

## Next Step

The next major extension is to add a **Submit Code** workflow.

Running tests will remain a temporary practice operation, while submission will store the student's final source code and evaluation result so that it can later be viewed by the administrator.

## Conclusion

Week 6–7 significantly improved the practical functionality of EduOS. The project moved beyond user provisioning and personalized desktop sessions and now provides an actual academic programming workflow. The C++ evaluator demonstrates how EduOS can eventually support controlled lab exercises and automated assessment within the operating-system environment.
