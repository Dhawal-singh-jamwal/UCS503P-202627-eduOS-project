## Overview

During this development phase, my main contribution was focused on system integration and persistence of the EduOS environment. Earlier, EduOS could successfully boot as a customized Arch Linux ISO with multiple student accounts and a separate administrator environment, but runtime changes were lost after restarting the virtual machine.

The major objective during this phase was therefore to make EduOS behave more like a persistent academic lab system rather than only a temporary live ISO.

## Admin Dashboard Integration

The administrator dashboard had already been implemented, but initially it was available only through the XFCE application menu.

I worked on integrating the dashboard directly into the administrator's graphical session so that it starts automatically when the `eduos` administrator logs in.

The solution used the XFCE/XDG autostart mechanism rather than launching the graphical application from a root-level systemd service.

This preserved the correct graphical environment, including:

- XFCE session variables
- X11 display access
- DBus session
- Correct administrator user identity

The admin application also checks the actual Linux UID and username before opening, so student accounts cannot launch the administrator dashboard.

The administrator dashboard was further updated to open in fullscreen mode by default, while still allowing the administrator to leave fullscreen mode when required.

## Diagnosis of ISO Build Failure

During rebuilding of the EduOS ISO, the ArchISO build failed while extracting packages and repeatedly reported `Write failed`.

The root filesystem still had sufficient disk space, so the issue was traced specifically to `/tmp`.

The system was using a `tmpfs` of approximately 7.5 GB for `/tmp`, which became completely full during the ArchISO build.

To solve this, the ArchISO working directory was moved from `/tmp` to a persistent directory inside the EduOS project partition.

This provided significantly more working space and made the ISO build process more reliable.

## Persistent EduOS State

A major issue identified during testing was that newly created student accounts disappeared after restarting the virtual machine.

This happened because EduOS was still being executed as a live ArchISO. Runtime filesystem changes were stored only in the temporary live environment.

To solve this, the system was redesigned to use a separate persistent EduOS state disk.

The new architecture separates:

- Immutable operating system files stored in the EduOS ISO
- Mutable academic and user state stored on a persistent virtual disk

The persistent state is mounted inside EduOS under:

`/var/lib/eduos`

This allows information such as the following to survive VM restarts:

- Dynamically created students
- Student metadata
- Account enabled/disabled state
- Password changes
- Lab assignments
- Assignment problem statements
- Student submissions

The persistent disk is reused each time the EduOS VM is started.

## Dynamic Student Account Persistence

Previously, only the built-in student accounts were recreated automatically during boot.

The provisioning workflow was extended so that student accounts created from the administrator dashboard can also be reconstructed from persistent EduOS state.

The design stores only necessary account information.

Plaintext passwords are not stored. Password hashes and other required account metadata are used for restoring Linux accounts safely.

The provisioning logic remains idempotent so that repeatedly starting EduOS does not create duplicate users or corrupt existing state.

## Current State

At the end of this phase:

- EduOS boots correctly using ArchISO
- The administrator dashboard starts automatically
- The admin interface can run fullscreen
- Student accounts continue to receive their own XFCE sessions
- New administrator-created students persist after reboot
- Persistent EduOS state is separated from the live ISO
- Lab and submission information can survive VM restarts
- ISO builds no longer depend on the limited `/tmp` filesystem

## Next Step

The next major system-level feature will be integration of the EduLab evaluation environment.

The current persistent submission structure provides a suitable foundation for later compiling and testing submitted programs without redesigning the student workflow.

## Conclusion

This phase improved EduOS from a temporary live prototype into a system capable of maintaining academic state between sessions. The addition of persistent runtime storage, improved administrator startup behaviour and more reliable ISO building makes the prototype more suitable for demonstrating a real university lab environment.
